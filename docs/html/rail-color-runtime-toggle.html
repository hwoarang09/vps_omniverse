레일 색 런타임 토글variantSet 방식이 왜 안 됐고, 값(value) 토글로 어떻게 고쳤나 — PointInstancer 갱신의 함정

개요

Omniverse Kit(USD Composer)에서 레일 색 realistic ↔ debug 토글 버튼(exts/vps.rail.tools)을 눌러도 화면의 레일 색이 안 바뀌던 문제를 다룬다. 원인은 PointInstancer 가 런타임의 "binding(관계) 변경"엔 갱신되지 않는다는 점이었고, 해결은 binding 을 건드리지 않고 머티리얼의 셰이더 입력 "값(value)" 만 바꾸는 것이었다.

  • 옛 방식 railColor variantSet — variant 가 proto 의 material:binding(관계)을 갈아끼움 → 런타임 토글 시 인스턴서 색 미갱신
  • 새 방식 타입별 전용 머티리얼에 고정 바인딩 + 버튼이 셰이더 inputs:diffuseColor/metallic/roughness 값만 Set → 런타임 갱신됨

학습 노트(NCP-OUSD 대비) 성격. 모든 서술은 코드/커밋 근거이며 파일:라인 으로 인용한다.

배경 — 레일은 어떻게 그려지나

레일은 단일 /World/Rails PointInstancer 로 그려진다. 색은 인스턴스가 참조하는 프로토타입(3개)의 머티리얼 바인딩에서 상속된다. 즉 "인스턴스 색 = proto 의 머티리얼"이라는 간접 구조라서, 무엇을 바꾸면 인스턴스가 다시 칠해지는가가 이 문서의 핵심이 된다.

사용자가 실제 겪은 흐름: (1) 원래 값 기반이라 색이 잘 보임/바뀜 → (2) variantSet 을 공부하며 그 방식으로 바꿔 usda 재생성 → 런타임 바인딩 스왑을 PointInstancer 가 못 읽어 깨짐 → (3) 오늘 값 기반으로 되돌려 복구. 사이 커밋(d738d3a 레이어 분리, 4ae9389 ruff)은 렌더 거동과 무관하다.

옛 방식 — variantSet

무엇을 author 했나

빌드 스크립트(당시 converter/convert_map_to_usd.py)가 /World/Protos 에 railColor variantSet 을 만들고, 각 variant 의 edit context 안에서 proto 의 머티리얼 바인딩을 다르게 걸었다.

variant바인딩 대상효과
realistic (기본)3 proto 전부 → /World/Looks/Rail_realistic알루미늄 그레이 공유 머티리얼
debug각 proto → /World/Looks/Rail_{green,pink,red}타입별 색 머티리얼

즉 두 variant 의 차이는 material:binding 관계의 타깃이다 (variant 마다 다른 머티리얼을 가리킴). 근거: 옛 convert_map_to_usd.py 의 variant edit context 안 MaterialBindingAPI(...).Bind(matof(key)).

# 옛 converter (convert_map_to_usd.py) — variant 가 binding 을 갈아끼움
vset = protos_prim.GetVariantSets().AddVariantSet("railColor")
for vname, matof in (("realistic", lambda k: mat_real),
                     ("debug",     lambda k: mat_dbg[k])):
    vset.AddVariant(vname)
    vset.SetVariantSelection(vname)
    with vset.GetVariantEditContext():
        for key in geo.RAIL_DEBUG_KEYS:
            UsdShade.MaterialBindingAPI.Apply(
                stage.GetPrimAtPath(f"/World/Protos/box_rail_{key}")
            ).Bind(matof(key))          # ← 바인딩(관계) 자체를 교체
vset.SetVariantSelection("realistic")

런타임 토글 코드

옛 확장(extension.py)의 버튼은 variant selection 만 바꿨다.

# 옛 extension.py — selection 전환
vs = prim.GetVariantSet("railColor")
nxt = "debug" if vs.GetVariantSelection() == "realistic" else "realistic"
vs.SetVariantSelection(nxt)         # ← 선택만 바꿈 → 내부적으로 binding 재배선

왜 안 됐나 (실패 메커니즘)

  1. 첫 sync 는 정상. Hydra 는 스테이지를 처음 로드/sync 할 때 binding 을 resolve 해서 PointInstancer 인스턴스에 머티리얼을 붙인다 → 이 시점에 선택된 variant 색은 제대로 렌더된다. (이는 일반 USD 사실이며, 빌드 기본값/fresh load 로 본 색이 맞게 나오는 이유다.)
  2. 런타임 재배선은 무시. 이미 sync 된 뒤 SetVariantSelection 으로 binding 을 갈아끼우면, 인스턴서의 인스턴스 머티리얼이 re-resolve(재해석)되지 않는다 (dirty 처리 누락). → 색이 안 바뀐다.
  3. FSD 무관. Fabric Scene Delegate 를 켜도 꺼도 동일하게 실패(실측). 즉 FSD 설정 문제가 아니라 "런타임 binding 변경 → 인스턴서 미갱신"이라는 구조적 문제다.

정정: 초기 작성본은 "variant 도입 후 런타임 토글이 처음부터 안 됐고, 사용자가 본 색은 정적(로드 시점)이었을 것"이라고 추측했으나 이는 틀렸다. variantSet 도입 직전(6b830d4)의 방식은 값 기반 고정 바인딩이라 런타임에서도 정상 동작했다(타임라인 표 참조). 깨진 것은 variantSet(바인딩 스왑) 방식으로 바꾼 뒤뿐이다.

런타임 — 셰이더 입력값 Set

새 extension.py 의 버튼은 variant 가 아니라 3개 머티리얼의 surface 셰이더 입력값을 직접 바꾼다. 셰이더는 Material.GetSurfaceOutput().GetConnectedSource() 로 찾고, 없으면 관례 경로 {mat}/Shader 로 폴백한다 (extension.py:66-79). 현재 모드는 self._debug bool 로 추적한다.

왜 되나 (성공 메커니즘)

Hydra 는 attribute 값 변경은 추적(dirty)해서 그 머티리얼을 쓰는 PointInstancer 인스턴스에도 re-shade 를 유발한다. 바인딩(관계)은 그대로 두고 값만 바꾸므로 런타임에 색이 갱신된다. (사용자 GUI 에서 실제 색 변경 확인됨.)

핵심 교훈

PointInstancer 는 런타임의 "binding(관계) 변경"엔 갱신되지 않고, "value(값) 변경"엔 갱신된다.

  • 정적 표현/이식성엔 variantSet 이 깔끔하다. 하지만 런타임 토글엔 값 변경 (또는 per-instance primvar, Fabric write)이 맞다.
  • 일반 원칙: author(빌드) 와 runtime 은 다른 층위다. 런타임 시각 변경은 "무엇을 dirty 시키는가"로 설계해야 한다 — 관계 재배선은 인스턴서를 dirty 시키지 못한다.
  • git 증거가 결론을 뒷받침한다. variantSet 도입 직전(6b830d4, convert_map_to_usd.py:82-87)의 동작하던 코드가 실제로 값 기반 고정 바인딩이었다 — 즉 "값 변경은 갱신, 바인딩 스왑은 미갱신"이 추측이 아니라 실측 회귀로 확인된 셈이다.
