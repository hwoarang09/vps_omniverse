USD 레이어 합성 (LIVRPS)레일 겹침을 런타임 분기 없이 비파괴로 정리한다 — 포폴 핵심 쇼케이스

문제 — 레일 raw 2줄의 겹침

VPS 맵의 각 edge 는 중심선이다. 이걸 렌더하려고 중심선을 좌우 ±gauge/2 로 오프셋해 레일 2줄(L/R)을 만든다 (geometry.py:790 dual_rail_segments_tagged). 문제는 분기·합류 노드와 곡선에서 서로 다른 edge 의 레일들이 같은 자리를 지나 겹쳐 보인다는 것. 그냥 두면 교차점이 지저분하고, 차량 주행 통로도 막힌 것처럼 보인다.

순진한 해법은 "겹치는 세그먼트를 빌드 때 빼고 그린다"이다. 하지만 그러면 원본(raw 2줄)이 사라져 무엇을 왜 가렸는지 되돌릴 수 없다. 디버깅·검증 때 raw 로 돌아갈 길이 없어진다.

근거: build_base.py:70-72 — "여기서 가려버리면 base 에 가릴 대상이 없어져 레이어 합성이 성립 안 함." base 는 일부러 raw 2줄 전부를 들고 있는다.

VPS(Three.js) 관점

Three.js 였다면 보통 런타임 분기로 푼다 — 겹침 목록을 들고 mesh.visible = false 를 매번 토글하거나, 모드별로 다른 지오메트리를 다시 빌드. 원본과 "정리본"이 같은 코드 경로에 얽혀 있어, 끄는 로직을 건드리면 원본도 깨진다.

USD 는 이걸 데이터 합성 문제로 바꾼다: 원본은 그대로 두고, "무엇을 숨길지"만 적은 별도 레이어를 위에 얹어 합성 결과를 만든다. 코드 분기가 아니라 레이어 on/off 다.

해법 — 레이어 합성으로 비파괴 정리

두 레이어 + 정적 합성

역할을 두 파일로 쪼갠다. base 는 원본만, line_cut 은 "숨김 지시"만. 합치는 건 정적 composed.usda 한 장.

  • base.usda raw 2줄 레일 전부 + 스테이션/장비/바닥/카메라 (build_base.py). 가린 것 없음.
  • line_cut.usda over "/World/Rails" { invisibleIds } 만 (build_line_cut.py). base 는 손도 안 댐.
  • composed.usda subLayers = [line_cut, base] 정적 stitch. 여는 건 이거.
레이어책임여기서 권위(authoritative)인 것생성
base.usda원본 지오메트리 positions, orientations, protoIndices (레일 45,136개) build_base.py
line_cut.usda겹침 숨김 오버라이드 invisibleIds (8,725개) build_line_cut.py
composed.usda합성 진입점 없음 (subLayers 5줄, 손으로 작성·맵과 무관) 정적

합성 강도: subLayers 는 앞이 강하다. 그래서 [line_cut, base] 순서로, line_cut 의 invisibleIds 가 base 위에 올라탄다. (composed.usda 상단 주석: "위(강)부터 아래(약)로 겹친다.")

합성 구조

line_cut.usda 실제 형태

build_line_cut.py:38-39 가 OverridePrim("/World/Rails") 로 over specifier prim 을 만들고 invisibleIds 만 적는다. 직렬화 결과는 경로가 중첩 over 로 펼쳐진다:

#usda 1.0

over "World"
{
    over "Rails"
    {
        int64[] invisibleIds = [214, 215, 217, 218, 467, ...]   # 8,725개
    }
}

over 는 "새로 정의(def)하지 않고 기존 prim 위에 덧쓰기"라는 뜻 — base 의 /World/Rails PointInstancer 를 새로 만들지 않고, 그 위에 invisibleIds 속성 하나만 추가로 얹는 비파괴 오버라이드다.

비파괴성과 인덱스 1:1 정합

이 방식이 성립하는 핵심 전제: invisibleIds 의 인덱스가 base PointInstancer 의 인스턴스 순서와 정확히 1:1 이어야 한다. 한 칸이라도 어긋나면 엉뚱한 레일이 사라진다.

그래서 base 와 line_cut 둘 다 같은 함수 geo.dual_rail_segments_tagged(edges, nodes) 를 같은 순서로 돌려 세그먼트 배열을 만든다. build_base.py:72 가 그 배열로 PointInstancer 를 채우고, build_line_cut.py:28-31 가 같은 배열에서 가릴 인덱스만 뽑는다.

인덱스 안정성 보장 (build_line_cut.py:11-13):

  • 양쪽 다 dual_rail_segments_tagged 단일 함수 공유 → 순서 동일.
  • make_instancer 가 ids 를 명시하지 않음 → instance id == 배열 인덱스.
  • hidden_seg_indices (geometry.py:826) 가 tagged 배열을 enumerate 하며 그 인덱스를 그대로 반환.

비파괴 확인은 단순하다: line_cut.usda 의 invisibleIds 를 비우거나 composed.usda 에서 line_cut subLayer 줄을 지우면 합성 결과가 즉시 raw 2줄로 복귀한다. base 는 한 번도 수정되지 않았다 (build_line_cut.py:45).

LIVRPS 개념 (학습용)

USD 에서 한 prim 의 최종 값은 여러 출처(composition arc)를 정해진 강도 순서로 합성해 결정된다. 그 순서의 머리글자가 LIVRPS 다 — 위가 강하고 아래가 약하다.

강도 순서

약자arc한 줄 의미
LLocal 이 레이어 스택에서 직접 쓴 opinion (subLayers 포함). 가장 강함.
IInherits 클래스(class) 상속 — 공통 속성 묶음.
VVariantSets 변형 선택(예: 이 프로젝트의 railColor realistic/debug).
RReferences 다른 에셋/prim 참조.
PPayloads 지연 로드(load-on-demand) 참조.
SSpecializes 기본값 성격 — 가장 약함(다른 모든 게 못 덮으면 적용).

이 프로젝트가 쓰는 것 — Local(subLayers)

이 문서의 합성은 LIVRPS 의 맨 위 L(Local) 한 종류만 쓴다. composed.usda 의 subLayers 가 그것이다. subLayers 내부에서도 앞 레이어가 더 강한 Local opinion 을 가지므로, [line_cut, base] 에서 line_cut 의 invisibleIds 가 base 를 이긴다.

참고로 base.usda 자체는 별도로 V (VariantSet railColor, build_base.py:99-107)도 쓴다 — realistic/debug 레일 색 토글. 이건 합성 강도 데모와는 별개 기능이다.

빌드 / 확인

변환은 빌드타임 스크립트다(앱 런타임 아님). 순수 usd-core(pxr)로 converter/ 안에서 실행한다.

cd converter
python build_base.py     ../input/fab_map ../out/base.usda
python build_line_cut.py ../input/fab_map ../out

# 합성 결과 보기
usdview ../out/composed.usda
# raw 2줄(정리 전) 보기
usdview ../out/base.usda

하위 hide 계산: hide_curve_edges(곡선 호 hide_curve_arc + 곡선 직선영역 방해 hide_curve_lead) 와 hide_linear_edges(직선 라인끊기)를 merge_hide 로 합쳐 hidden_seg_indices 로 인덱스화한다 (build_line_cut.py:29-31). 이 hide 규칙 자체는 별도 converter 문서 영역.
